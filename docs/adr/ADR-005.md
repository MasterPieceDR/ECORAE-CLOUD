# ADR-005: Las reglas de negocio viven en PostgreSQL y la API es delgada

**Contexto.** Las reglas RN-01 a RN-09 deben cumplirse por cualquier canal (web, asistente MCP, scripts) y probarse
de forma reproducible (RNF-04, RNF-09).

**Decisión.**
- Toda escritura pasa por funciones `api.fn_*` (`SECURITY DEFINER`) que validan permisos y reglas.
- Las lecturas pasan por vistas `api.v1_*` con `security_invoker` y seguridad por fila (RLS).
- Cada petición abre una transacción con `api.fn_iniciar_contexto(usuario, canal, request_id)`.
- Los logins de servicio `ecoraee_api_svc` y `ecoraee_mcp_svc` no tienen INSERT/UPDATE/DELETE directos.
- La API autentica, abre el contexto, llama a la función y traduce los errores `EC4xx` a HTTP.

**Alternativas.** Reglas en la capa de servicios de Python con un ORM: más conocido, pero cada canal debería repetirlas
y la base quedaría expuesta a escrituras que se saltan las reglas.

**Consecuencias.** Las 84 pruebas de `06_pruebas.sql` validan las reglas sin la API. Los cambios de reglas se hacen con
scripts numerados (`database/17_*.sql`, …). La lógica en PL/pgSQL es la razón principal para elegir **Amazon RDS for
PostgreSQL** y no DynamoDB (ADR-015).
